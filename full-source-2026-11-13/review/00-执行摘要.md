## ⚠️ [P1·确认即升 P0] PY-09 管理凭据文件位于 Web 目录，可能被 HTTP 直接读走
- **位置**：`cloud/var/www/logview/app.py:13`（`AUTH_FILE = "/var/www/panel/panel-auth.json"`）、`:31-34`（会话令牌 = `时间戳.HMAC(secret,时间戳)`）、`:28-29`（`pbkdf2_hmac` 口令哈希）
- **为什么是高危**：该 JSON 同时含 `salt`、`hash` 和**签发会话令牌的 HMAC secret**。secret 泄露 → 攻击者可**本地算出合法会话令牌，完全不需要口令**即可进入管理面板（已被 R1 用原始函数证实：伪造 cookie → `GET /` 返回 200 管理页）。该面板能改 Cloudflare 全部安全开关、能让全站进入 503 DDoS 模式、能看到日志与发信记录。**拿到即等于接管整域安全配置**；hash 泄露还可离线爆破口令。
- **为什么无法复现**：① 交付包**没有任何 nginx 站点配置**，`panel.*` 是静态根还是反代到 Flask 无从得知；② `panel-auth.json` 由未交付的 `panel.service` 生成，目录权限位未知；③ 唯一能确认的办法是向被审域名发请求，而本项目**明令禁止访问生产环境**。
- **要在自有环境确认**：`nginx -T | grep -nE 'server_name|root |proxy_pass'` 看 `panel.*` 的 root；再 `curl -sS -D- https://panel.<你的测试域>/panel-auth.json`，**期望 403/404**；若 200 且含 `"secret"` → 直接按 P0 处理。
- **先做的补救（不必等确认）**：把凭据文件移出 Web 根（`/etc/logview/panel-auth.json`，`chmod 600`）、nginx 加 `deny all`、**轮换 secret 使所有旧会话失效**。
- **复现物**：`03-复现包/py-panels/PY-09/`（R3 说明 + 影响链 R1 证明）

## ⚠️ [P1] MCG-02 Minecraft 准入只按"玩家名"判定，离线模式可完全冒名顶替
- **位置**：`cloud/opt/build/mcgate/src/com/lzj/mcgate/Gate.java:77,79,143,167`、`Backend.java:55`、`cloud/var/www/chat/mc-api.php:46-53`

## ⚠️ [P1] SH-01 心跳文件内容进入 bash 算术展开 → root 命令注入
- **位置**：`cloud/usr/local/sbin/failover.sh:26-31`（`v=$(cat "$HB_FILE")` → `$(( now - v ))`）、`:189,195,234`；`home-mc-alive.sh:9-14`
- **为什么是高危**：bash 算术求值会**把变量的值再当表达式递归求值**，其中的 `$(...)` 会被执行。也就是说**只要 `/root/failover/heartbeat` 的内容可控，root 就执行任意命令**。而这两个脚本由 root 的 cron 执行、负责自动切换 DNS 与启停服务器——一旦失守，是"无鉴权控服务器"。同文件对 `home_ip` 做了 `*[!0-9.]*` 过滤，**唯独心跳/计数器没有**，属明显遗漏。
- **为什么无法复现**：① 本机没有任何 bash（无 WSL/Git-Bash/MSYS/Cygwin），无法跑 `$(( ))` 的真实语义；② 需要 `/root` 写权限；③ **最关键的：写心跳的家庭侧脚本未交付**（`06-审查盲区` 第 13 项），因此无法证明写入内容可以由低权进程/外部输入影响——这也是本条只敢判"高可能"而不是"确认"的原因。
- **要在自有环境确认**：Linux 测试机 `printf 'x[$(touch /tmp/PWNED)]' > /tmp/hb`，把 `hb_age()` 的 `HB_FILE` 指向它执行，看 `/tmp/PWNED` 是否出现；确认后再核查家庭侧写入路径的权限与数据来源。
- **修复**：读入后 `v=${v//[^0-9]/}` + 长度上限 + 非法内容显式告警（`fix.md` 有完整改法）。
- **复现物**：`03-复现包/sh-infra/SH-01/`（等价模型证明递归求值；含 5 行 bash 验证片段）

## ⚠️ [P1] SH-02 唯一缓解手段（503 模式）会静默失效、失败后永不重试，`off` 还能把 503 写回（自锁）
- **位置**：`cloud/usr/local/sbin/ddos-mode.sh:2,10,32,38-42`；`cloud/usr/local/sbin/ddos-monitor.py:65,129-131`
- **为什么是高危**：`ddos-mode.sh` 是"正在被攻击时"唯一能止血的开关，但它有三处叠加缺陷：① `set -euo pipefail` + `NAMES=$(grep|sed|…|tr)`，`grep` 无匹配（rc=1）就会在写配置前中止；② `touch /run/ddos-mode` 在 `nginx -t` **之前**，而监控端不看返回码且只在 `not is_mode` 时重试 → **失败一次就再也不会尝试开启 503**；③ `off` 回滚的目标是"本次调用开始时的配置"（很可能就是 503 配置本身）→ 一旦 `nginx -t` 因无关原因失败，就形成"退不出 503"的自锁，叠加 `SH-07`（面板域名不在 `ddos.*` 就被 503）时只能 SSH 救火。
- **为什么无法复现**：本机无 bash/nginx/`/etc/nginx`；需要真实 `sites-enabled/*`（**未交付**）才能构造正确的/错误的 `NAMES`；自锁需要"`nginx -t` 因别的原因失败 + 攻击进行中 + 面板不可达"三者同时成立。
- **复现物**：`03-复现包/sh-infra/SH-02/`（Python 等价模型逐条演示 rc 传播、标志时序、回滚目标）
