== 判定 ==
  [符合] jti = 12 字节随机(96 bit), 在 HMAC 覆盖的 payload 内, exp=120s;
         fopen(...,'x') 是 O_EXCL 原子创建 => 同一令牌第二次使用必然失败;
         签名比较用 hash_equals(常量时间), 实现方式正确。
         (注: 该声明针对 approve.php 短链审批的是另一套 token, 别混淆)
  [缺陷1] 先烧令牌后鉴权: 第 22 行消费 jti, 第 24/29/30 行才校验 uid 归属、动作白名单、
          cfg.permissions。任何持有他人令牌的人(令牌泄露/被日志带出)都能让该审批
          永远失败 —— 单 token 的 DoS, 而且受害者重试时得到的是'批准已过期或无效'。
  [缺陷2] /var/lib/chat-ai/used/ 只写不删(116-120 行无清理逻辑), 每批准一次一个文件,
          永久累积(单目录 inode 增长); 目录不可写时 fopen 失败 -> 所有审批一律 403,
          且 @ 抑制了错误原因, 运维难排查。
  [缺陷3] 令牌未与调用方绑定(无 IP/会话指纹), 只靠 uid 字段; 群主账号会话被盗即可
          重放未消费的 token(窗口 120s)。这属于既有权限模型, 但一次性只有 120s 强度。

== 建议 ==
  1) 把 uid/动作鉴权前移到 ai_verify_action 之前(先验身份再烧 jti):
     先解析 payload(不落盘)校验 uid==me.id 与动作许可, 最后再 fopen 'x' 占位;
  2) used 文件按日期分目录 + cron 清理(>7 天), 或用 DB 唯一键替代文件;
  3) 目录不可写时返回 500 并记日志, 不要伪装成'令牌过期'。
